# Wire Framework Demos — Build Playbook

**Status**: Approved 2026-05-31 — ready to build
**Target repo**: `rittmananalytics/wire-demos` (new, public)
**Author**: Mark Rittman + Claude (Opus 4.7)

This playbook is the spec for three self-contained Wire Framework demos. It exists so the build can proceed without re-deriving design decisions, and so anyone picking up the work later can do so without rereading the originating conversation.

---

## 1. Scope and locked decisions

Three demos in one repo. Each launches from a single command, narrates itself as it runs, executes real Wire commands against a real local DuckDB warehouse, and is fully re-runnable.

| Decision | Choice | Rationale |
|---|---|---|
| Runner | `claude -p` headless (bash) | Keeps the installed Wire plugin in scope; one-line per step; no SDK auth |
| Reviews | Auto-approved, narrated as stubbed | Demos can't block on human input; honest about the simulation |
| Repo location | New public repo `rittmananalytics/wire-demos` | Clean separation from framework source; clone-and-run friendly |
| Warehouse | DuckDB via `dbt-duckdb` | No external DB; real `dbt build` works |
| LookML | Generate + syntactic validate only | Looker can't run locally; use `wire:looker-dashboard-mockup` for visual output |
| Model | Haiku 4.5 default; Sonnet for heavy generation | Faster, cheaper, output is comparable for structured generation |
| Distribution | Asciinema cast per demo as fallback | Live runs are headline; recorded casts cover offline/conference floor cases |

## 3. The synthesized client — Acme Coffee Roasters

D2C subscription coffee business. Chosen because the domain (orders, customers, subscriptions, shipments, marketing) is broadly understood and exercises every Wire dbt layer without being toy-scale. Same client across all three demos with different scopes.

### 3.1 Source systems and tables

| System | Tables | Rows (seed) | Notes |
|---|---|---|---|
| Shopify | `customers`, `orders`, `order_lines`, `products`, `subscriptions` | ~10k orders, ~3k customers | Primary commerce |
| Stripe | `charges`, `refunds`, `subscriptions`, `invoices` | ~12k charges | Payments |
| Klaviyo | `events`, `campaigns`, `flows`, `lists` | ~30k events | Marketing |
| Shipstation | `shipments`, `tracking_events` | ~10k shipments | Fulfilment |
| GA4 | `sessions`, `events`, `users` | ~50k sessions | Web analytics |

Total ~115k rows. Generated by a deterministic Python script (`shared/client/sources/generate.py`) seeded with a fixed RNG so the data is identical on every clone.

### 3.2 SoW content shape

The bundled SoW is a real 6-page document with:
- Background (Acme's growth, why they need this)
- Scope (5 source systems, 4 reporting domains)
- Out of scope (legal/finance, customer support)
- 12 open questions (OQ-1 through OQ-12) — at least one tagged as build-blocker, so `problem-definition-validate` has something real to catch
- 4 data quality concerns (DQ-1 through DQ-4)
- 8 named stakeholders matching `org/stakeholders.md`
- Acceptance criteria
- A pricing table (so `kickoff-generate` has commercial detail to populate)

### 3.3 Call transcripts

Three transcripts of ~600–800 lines each. Plain text, conversational, with the four-tag content (problem statements, current pain, desired outcome, success criteria) that `stakeholder-interview-generate` expects. Written, not LLM-generated, to keep them deterministic.

## 4. Shared infrastructure

### 4.1 Narrator API (`shared/narrator.sh`)

Sourced by every demo step. Provides:

```bash
narrate "Step 4 — Wire generates the conceptual model from the SoW…"
narrate_long <<'EOF'
The conceptual model is the entity-relationship diagram the team agrees on
before any code is written. Wire reads the SoW + bundled call transcripts and
produces a mermaid ERD plus a narrative…
EOF
pause                      # Honours DEMO_MODE: "auto" returns immediately, "interactive" waits for enter
show_file path/to/file.md  # Cats the file with syntax highlighting via bat if available
show_command "$cmd"        # Prints the command in a coloured box before running it
section "Phase 2 — Design"  # Big banner separator
```

Colour scheme: cyan for narration, yellow for commands, green for success, red for errors, dim grey for file content. ANSI-only (no `tput`) so it works inside `tmux`, `screen`, and piped to `tee`.

`DEMO_MODE` env var:
- `auto` (default for CI) — no pauses, no `read -p`
- `interactive` (default for live demos) — pauses after each `narrate`
- `silent` — no narration output, just commands (for debugging)

### 4.2 Runner (`shared/runner.sh`)

Sourced by every demo step. Provides:

```bash
run_wire "/wire:requirements-generate releases/01-data-foundation"
# → shells to: claude -p "/wire:requirements-generate releases/01-data-foundation" \
#              --output-format stream-json \
#              --permission-mode acceptEdits \
#   tees output to logs/<demo>/step-<N>-<cmd>.log
# → returns exit code from claude

run_dbt build --select stg_shopify__orders
# → shells to: dbt --profiles-dir ./shared/profiles build --select stg_shopify__orders
# → tees to logs/<demo>/dbt-<timestamp>.log

run_dbt_target_path
# → echoes the target dir (used by validate.sh)
```

Error handling: if `run_wire` exits non-zero, the demo prints the last 50 lines of the log, asks whether to retry (in `interactive` mode) or exits (in `auto` mode). No silent failures.

### 4.3 Auto-approve (`shared/auto_approve.sh`)

Wire's `-review` commands prompt for approval via `AskUserQuestion`. In headless `claude -p` mode, that prompt is bypassed automatically — but the spec also looks for stakeholder feedback in chat. The wrapper appends ``"Approved by demo operator — no changes requested."`` to the prompt so the review command has reviewer input to record. The narrator says aloud:

```
narrate_long <<'EOF'
In a real engagement, your sponsor reviews this artifact and either approves
it, requests changes, or asks for more discussion. For the demo, we auto-
approve so the flow continues.
EOF
```

This appears once per demo, not on every review.

### 4.4 DuckDB profile (`shared/profiles/duckdb_profile.yml`)

```yaml
acme:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: ./warehouse.duckdb
      threads: 4
      extensions:
        - httpfs
        - parquet
```

The `.duckdb` file is per-demo (`demo1-full-lifecycle/warehouse.duckdb`), git-ignored, and recreated on every demo run.

### 4.5 BQ → DuckDB macro shims (`shared/macros/bq_to_duckdb/`)

Wire generates BigQuery-targeted SQL. DuckDB is broadly compatible but a small number of functions need shimming:

| BQ function | DuckDB equivalent | Shim macro |
|---|---|---|
| `safe_cast(x as type)` | `try_cast(x as type)` | `safe_cast.sql` |
| `current_timestamp()` | `now()` | `current_timestamp.sql` |
| `date_diff(d1, d2, day)` | `(d1 - d2)::integer` | `date_diff.sql` |
| `parse_json(str)` | `json(str)` | `parse_json.sql` |
| `to_json_string(obj)` | `json_string(obj)` (cast) | `to_json_string.sql` |
| `generate_uuid()` | `uuid()` | `generate_uuid.sql` |
| `unnest(arr) as x` | `unnest(arr) as t(x)` | Handled by dbt config |
| `_TABLE_SUFFIX` / sharded tables | Not used in seed data | n/a |

Each shim is a dbt macro that wraps DuckDB's equivalent in a name that matches BQ's. dbt models written for BQ then run unmodified on DuckDB by referencing these macros.

Documented limits: BQ-specific patterns Wire doesn't currently emit but would break if used — `ML.*`, geospatial functions, BQ ML, `INFORMATION_SCHEMA` queries. README documents these.

## 5. Demo 1 — Full lifecycle

**Release type**: `full_platform`. ~8–12 minutes live.

**Goal**: prove end-to-end that Wire can take a SoW, produce every artifact through deployment-ready dbt, hit a real failure, fix it, and surface a final dashboard mockup — all without leaving the local machine.

### 5.1 Step table

| # | Narration topic | Command | Expected artifact / output |
|---|---|---|---|
| 1 | Install Wire from scratch | `claude` `/plugin marketplace add rittmananalytics/wire-plugin && /plugin install wire@rittman-analytics && /reload-plugins` | Plugin installed |
| 2 | Engagement setup | `run_wire "/wire:new"` (scripted answers via heredoc) | `.wire/engagement/context.md`, `.wire/releases/01-data-foundation/status.md` |
| 3 | Collect materials | `cp -r shared/client/* .wire/engagement/` | SoW, calls, org, sources in place |
| 4 | **Delivery playbook — the demo's own roadmap** | `run_wire "/wire:playbook-generate releases/01-data-foundation"` | `planning/delivery_playbook.md` — BPMN diagram of every artifact in the release, used here as the table of contents for what follows |
| 5 | Show the playbook on screen | `show_file releases/01-data-foundation/planning/delivery_playbook.md` (narrator renders the mermaid BPMN inline if `mdcat`/`glow` is available) | Viewer sees the full roadmap before the rest executes |
| 6 | Requirements | `run_wire "/wire:requirements-generate releases/01-data-foundation"` then `-validate` then `-review` | `requirements/requirements_specification.md`, validation PASS, review approved |
| 7 | Conceptual model | `-generate` / `-validate` / `-review` | `design/conceptual_model.md` with mermaid ERD |
| 8 | Pipeline design | `-generate` / `-validate` / `-review` | `design/pipeline_architecture.md` with DFD |
| 9 | Data model | `-generate` / `-validate` / `-review` | `design/data_model_specification.md` with physical ERD |
| 10 | dbt staging | `run_wire "/wire:dbt-generate releases/01-data-foundation --layer staging"` | `models/staging/*.sql` for all 5 source systems |
| 11 | First dbt build | `run_dbt deps && run_dbt seed && run_dbt build` | All staging models built, seeds loaded into DuckDB |
| 12 | Planted fault | `cp _seed/faults/stg_shopify__orders.sql models/staging/shopify/` | One model overwritten with a `not_null` test that will fail |
| 13 | dbt-validate finds it | `run_wire "/wire:dbt-validate releases/01-data-foundation"` | Validation report flags the failing test |
| 14 | Diagnosis (narrator quotes Wire's dbt convention) | (narrator block, no command) | — |
| 15 | Fix via Claude | `claude -p "fix the failing not_null test in stg_shopify__orders.sql — the email column has a known null for guest orders; treat email as nullable"` | Model edited |
| 16 | dbt-validate passes | `run_wire "/wire:dbt-validate releases/01-data-foundation"` | PASS |
| 17 | Re-build | `run_dbt build` | All models green |
| 18 | Semantic layer | `run_wire "/wire:semantic_layer-generate releases/01-data-foundation"` + syntactic validate | `semantic_layer/lookml/*.view.lkml`, `*.model.lkml` |
| 19 | Dashboard mockup | `run_wire "/wire:looker-dashboard-mockup"` with a prepared mockup spec | `dashboards/mockup.html` |
| 20 | View final output | `open dashboards/mockup.html` (Linux: `xdg-open`) | HTML opens in default browser |

**Pedagogical note on step 4**: putting `playbook-generate` immediately after `/wire:new` (rather than at the end) gives the viewer the demo's own table of contents up front. They see the BPMN diagram first; the rest of the demo then traces a path through it. The mermaid BPMN rendered in step 5 should match what unfolds in steps 6–20 — that match is itself part of the message: *Wire told you what was coming, then did exactly that.*

### 5.2 Scripted answers for `/wire:new`

Step 2 needs to answer 9 prompts non-interactively. Approach: a heredoc piped into `claude -p` with each answer on its own line, in order:

```
Acme Coffee Roasters
acme_coffee_data_platform
Mark Rittman (demo)
A
.wire/engagement/sow.md
Full platform
01-data-foundation
No, skip issue tracking
No, skip document store
Yes, create it
```

If `/wire:new`'s prompt order changes, this breaks. Mitigation: pin the demo to a specific Wire plugin version (`@3.5.4` or whatever is current at build time).

### 5.3 Planted fault details

`_seed/faults/stg_shopify__orders.sql` is a copy of the expected generation with one modification: a `not_null` test on `email` that the seed data violates (guest orders have null emails). The `dbt-validate` command catches this via the dbt test run. The fix in step 13 either removes the test or changes it to `not_null` with a `where order_type != 'guest'` clause — Claude makes the call.

### 5.4 Time-budget contingency

If steps 6–9 (requirements → design) run long, the alternative is to ship them pre-generated in `_seed/skip-ahead/` and have those steps *display* the artifacts rather than regenerate. Demo loses some authenticity but gains 4–6 minutes. Decision: ship live by default, document the pre-generated path in the README as a `DEMO_SPEED=fast` option. The playbook (step 4) is never skipped — it's the cheapest step and the most pedagogically valuable.

## 6. Demo 2 — Fix an issue in an existing project

**Release type**: `dbt_development` (smaller scope, faster start). ~4–6 minutes live.

**Goal**: show Wire's value on an in-flight project — not as a generator but as a guardrail. Demonstrate `/wire:start`, the dbt-development skill catching a convention violation, and the fix loop.

### 6.1 Starting state (`_seed/`)

- `.wire/engagement/context.md` + `.wire/engagement/sow.md` (same Acme client, different scope: "extend the warehouse with a marketing attribution mart")
- `.wire/releases/01-marketing-mart/status.md` showing requirements + data_model as complete-approved, dbt as generated-validate-failing
- `dbt/` with the project already built and one warehouse model deliberately wrong: `fct_orders.sql` uses `customer_id` as the FK column name instead of `customer_fk` (violates the Wire dbt naming convention)

### 6.2 Step table

| # | Narration | Command | Expected output |
|---|---|---|---|
| 1 | Inherit an in-flight project | `cp -r _seed/.wire .` and `cp -r _seed/dbt .` | Starting state in place |
| 2 | What's here? | `run_wire "/wire:start"` | Lists `01-marketing-mart`, selects it |
| 3 | Where are we? | `run_wire "/wire:status releases/01-marketing-mart"` | Shows dbt validate as failing |
| 4 | Run the validate | `run_wire "/wire:dbt-validate releases/01-marketing-mart"` | Naming convention violation: `customer_id` should be `customer_fk` |
| 5 | Why does it matter? | (narrator quotes `wire/skills/dbt-development/SKILL.md` on `_fk` convention) | — |
| 6 | Fix it | `claude -p "in models/warehouse/fct_orders.sql, rename the customer_id column to customer_fk to match Wire dbt conventions, and update any downstream refs in models/warehouse/. Don't change the source column name in stg_shopify__orders.sql."` | File edited correctly |
| 7 | Re-validate | `run_wire "/wire:dbt-validate releases/01-marketing-mart"` | PASS |
| 8 | Confirm runtime | `run_dbt build --select fct_orders+` | Green |
| 9 | Sign off | `run_wire "/wire:dbt-review releases/01-marketing-mart"` (auto-approved) | Review approved |

### 6.3 Alternative fault library

The repo ships three planted faults. The default demo uses Fault A. The others are documented in `demo2-fix-an-issue/README.md` for re-recording or variant runs.

| ID | Fault | Caught by |
|---|---|---|
| A (default) | `customer_id` instead of `customer_fk` in `fct_orders.sql` | `dbt-validate` naming check |
| B | Missing `not_null` test on PK in `dim_customer.yml` | `dbt-validate` testing-coverage check |
| C | `int_orders.sql` references a non-existent column `order_status_v2` | `dbt-validate` compilation step |

## 7. Demo 3 — Dashboard-first

**Release type**: `dashboard_first`. ~12–15 minutes live.

**Goal**: show the inverted workflow — mockups → viz catalog → data model → seed data → dbt → semantic layer → dashboards on synthetic data, then `data_refactor` to swap in "real" data.

### 7.1 Starting state (`_seed/`)

- A `shared/client/mockup_spec.md` describing what the dashboards should look like (3 dashboards, 14 charts total). Used as input to `mockups-generate`.
- Two seed datasets: `_seed/seed_data_v1/` (synthetic, used to back the prototype) and `_seed/seed_data_real/` (different schema, simulating what the real Shopify export looks like — column renames, an extra nested JSON field, different date format).

### 7.2 Step table

| # | Narration | Command | Expected output |
|---|---|---|---|
| 1 | Engagement setup | `run_wire "/wire:new"` (type=dashboard_first) | `.wire/` structure for dashboard_first |
| 2 | Mockups first | `run_wire "/wire:mockups-generate releases/01-revenue-dashboards"` | HTML mockups via `looker-dashboard-mockup` skill |
| 3 | View mockups | `open dashboards/mockup.html` | Browser opens |
| 4 | Viz catalog | `run_wire "/wire:viz_catalog-generate releases/01-revenue-dashboards"` | `design/viz_catalog.md` — 14 charts catalogued |
| 5 | Data model from charts | `run_wire "/wire:data_model-generate releases/01-revenue-dashboards"` then `-validate` then `-review` | Model derived from what dashboards need |
| 6 | Seed data | `run_wire "/wire:seed_data-generate releases/01-revenue-dashboards"` then `-validate` then `-review` | Synthetic CSVs matching the model |
| 7 | dbt build on seeds | `run_wire "/wire:dbt-generate"` + `-validate` then `run_dbt seed && run_dbt build` | Warehouse built on seed data |
| 8 | Semantic layer | `run_wire "/wire:semantic_layer-generate"` | LookML views/explores |
| 9 | Working dashboards | `run_wire "/wire:dashboards-generate"` — re-renders mockup HTML against seed data | `dashboards/v1.html` |
| 10 | View prototype | `open dashboards/v1.html` | Live charts on synthetic data |
| 11 | Real data lands | `cp -r _seed/seed_data_real/* dbt/seeds/` | New columns/format appear |
| 12 | Refactor plan | `run_wire "/wire:data_refactor-generate releases/01-revenue-dashboards"` then `-validate` then `-review` | Mapping doc: synthetic → real |
| 13 | Apply refactor | `run_wire "/wire:dbt-generate --mode refactor"` then `run_dbt build` | Warehouse rebuilt against real-shaped seeds |
| 14 | Same dashboards, real data | `run_wire "/wire:dashboards-generate"` and re-open | `dashboards/v2.html` — same charts, real-shaped data |

### 7.3 Why two seed datasets

The `seed_data_real` set deliberately differs from `seed_data_v1` in three specific ways, so the refactor has something concrete to do:
1. `customer_id` is now `cust_id`
2. Order line items are nested as JSON instead of flat rows
3. Dates are ISO strings instead of timestamps

These are realistic Shopify-export gotchas. `data_refactor-generate` writes the mapping; `dbt-generate --mode refactor` updates the staging models to handle them.

## 8. Reset semantics

Each demo's `_seed/` is the immutable starting state. The runner's `reset` action:

```bash
make reset                 # Resets all three demos
make reset DEMO=demo1      # Resets just one
```

Per-demo `reset.sh`:
1. `rm -rf <demo>/.wire <demo>/dbt <demo>/dashboards <demo>/warehouse.duckdb <demo>/logs`
2. `cp -r <demo>/_seed/. <demo>/` (restores starting state)
3. `cd <demo> && git clean -fd && git checkout -- .` (only inside the demo dir, never touches user's other files)

`reset` is also called at the start of every demo run unless `DEMO_RESET=false`. This means re-running a demo is always clean.

## 9. Validation

Each demo ships `expected_artifacts/` — a golden snapshot of what "done" looks like. After a demo run, `validate.sh` does:

1. **Existence check**: every expected file exists in the working dir.
2. **Structure check**: dbt manifest has the expected models / tests / sources counts.
3. **Tolerant content check**: for LLM-generated markdown, only check headings + section names exist, not prose. (Quoting from the playbook's risk section: don't golden-file LLM prose.)
4. **dbt run-results check**: the last `dbt build` produced a `run_results.json` with no failures.

`validate.sh` exits 0/non-zero. CI runs every demo in `DEMO_MODE=auto` and asserts validation passes.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| LLM output varies between runs (prose, ordering, model counts) | Tolerant validation (§9); narrator allows for differences; pin Wire version |
| dbt-duckdb compatibility limits | Macro shims (§4.5); document unsupported BQ patterns in README |
| Plugin version drift breaks `/wire:new` answer ordering | README pins plugin version: "this demo is tested against Wire @3.5.4"; demo fails fast if mismatched |
| Claude Code not authenticated | `doctor.sh` checks `claude` is on PATH and authenticated before any demo starts |
| API outage during live demo | Asciinema cast as fallback (`make demo1-cast`) |
| `claude -p` cost on conference floor | `DEMO_MODEL=haiku` env var routes through Haiku 4.5 explicitly |
| Demos accumulate state if run nested | Per-demo working dirs; reset is mandatory in `auto` mode |

| Day | Work | Definition of done |
|---|---|---|
| 1 | `shared/` — narrator, runner, auto-approve, DuckDB profile, macro shims, Acme client materials | `shared/doctor.sh` passes; a one-step "hello world" test runs `/wire:status` end to end |

Effort ~5–6 working days. Two-day buffer for plugin version surprises and LookML/DuckDB edge cases gives ~8 days end to end.

## 12. Open questions / future work

- **Fourth demo: `sop_discovery`.** The current three cover full_platform, dbt_development, and dashboard_first. SOP discovery would round out the discovery side. Defer until v1 lands.
- **`make demo-record`** that drives the demo and produces an asciinema cast automatically. Useful but not blocking.
- **Per-step retry**: if a `claude -p` call returns flaky output, allow the runner to retry once before failing. Worth adding after we see how often this happens in practice.
- **Telemetry consent**: demos run `claude -p` which emits prompt telemetry to `ra-development`. README should disclose this and offer an opt-out (`DEMO_TELEMETRY=false` → set the relevant env var that disables Wire's logging hook).
