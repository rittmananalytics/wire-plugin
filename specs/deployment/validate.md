# deployment Validation Command

## Purpose

Validate the deployment plan generated by `/wire:deployment-generate`: pipeline connections are healthy (existing pre-flight gate), every cutover step has a paired rollback action or an explicit no-rollback recovery note, and the plan's connection/credential references match the real state of the project rather than being stale or invented.

## Usage

```bash
/wire:deployment-validate YYYYMMDD_project_name
```

## Prerequisites

- deployment must be generated (`/wire:deployment-generate` complete)

## Workflow

### Step 1: Verify deployment Exists

**Process**:
1. Check that `deployment.generate == complete` in status.md
2. Verify generated files exist

**If not generated**:
```
Error: deployment not generated yet.

Run `/wire:deployment-generate <project>` first.
```

### Step 2: Pipeline Connection Pre-flight Check

If `artifacts.pipeline.generate == complete` in status.md, follow `wire/specs/utils/pipeline_tool_status.md` to check pipeline connection health before proceeding.

| Health result | Action |
|--------------|--------|
| `healthy` | Proceed to Step 3 |
| `degraded` | Warn the user, list stale/warning connections, proceed |
| `unhealthy` | **FAIL** deployment validation — broken pipeline connections must be fixed before the platform can go live |

If `pipeline.generate != complete`, skip this check (pipeline may not be in scope for this project).

### Step 3: Run Validation Checks

**Validation Checklist**:

| Check | Rule | Severity |
|-------|------|----------|
| Pipeline connections healthy | All connections `setup_state == connected` and last sync succeeded (via pipeline_tool_status) | Critical |
| Every cutover step has a rollback action | Every row in the plan's "Cutover Sequence" table has a non-empty "Rollback" value — either a concrete undo action or an explicit "no rollback possible; requires [specific manual recovery]" note | Critical |
| Cutover order respects dependencies | pipeline pre-flight precedes dbt deployment; dbt precedes semantic_layer; semantic_layer precedes dashboards — no step depends on an artifact that comes later in the sequence | Major |
| Plan's connection list matches pipeline_tool_status | If `pipeline.generate == complete`, every connection named in the plan's "Pre-flight" table exists in the live `pipeline_tool_status.md` result — no orphaned or invented connection names | Major |
| Environments/credentials match requirements scope | Every environment and credential requirement listed matches what's actually scoped in `requirements/requirements_specification.md` — no undefined environment introduced | Major |
| Post-cutover verification checklist present | The plan includes a non-empty "Post-Cutover Verification" checklist | Info |

### Step 4: Generate Validation Report

**Output Format**:

```
## deployment Validation: [PROJECT_NAME]

**Status:** PASS | FAIL

### Validation Results

| Check | Status | Notes |
|-------|--------|-------|
| Pipeline connections healthy | ✅ | |
| Every cutover step has a rollback action | ⚠️ | Step 3 (orchestration schedule switch) has no rollback listed |
| Cutover order respects dependencies | ✅ | |
| Plan's connection list matches pipeline_tool_status | ✅ | |

### Next Steps

1. **Review with stakeholders**: `/wire:deployment-review <project>`
```

### Step 5: Update Status

**Process**:
1. Read `status.md`
2. Update artifacts.deployment section:
   ```yaml
   deployment:
     generate: complete
     validate: pass | fail
     review: not_started
     validated_date: 2026-02-13
   ```
3. Write updated status.md

### Step 6: Sync to Jira (Optional)

Follow the Jira sync workflow in `specs/utils/jira_sync.md`:
- Artifact: `deployment`
- Action: `validate`
- Status: the validate state just written to status.md (pass/fail)

## Edge Cases

### Validation Failures

If checks fail:
- Set validate status to `fail`
- List all issues, distinguishing an unhealthy pipeline connection (Critical, blocks go-live) from a missing rollback note (Critical, but fixable by editing the plan) from a stale connection reference (Major)
- Suggest fixes
- User must fix and re-validate

### Pipeline Connections Degraded, Not Unhealthy

Per Step 2's existing table, `degraded` connections warn but don't block. If Step 3's other checks also pass, report `PASS WITH WARNINGS` rather than `FAIL` — a stale-but-connected sync is not a reason to block go-live on its own.

## Output

This command:
- Validates deployment completeness and quality
- Updates `status.md` with validation results
- Provides actionable feedback if issues found
