# Droughty dbt Tests Command

## Purpose

Run `droughty dbt` to generate `schema.yml` test declarations from the deployed warehouse schema. Droughty applies deterministic naming-convention rules — columns ending in `_pk` get `unique` + `not_null` tests, date/datetime columns get valid-range tests, low-cardinality columns get `accepted_values` tests — providing exhaustive pattern coverage across every column in scope.

This command augments (not replaces) any `schema.yml` tests already generated by `/wire:dbt-generate`. Conflicts are handled explicitly — no silent overwriting.

**Run after `dbt run`** — Droughty reads the deployed tables from the warehouse, so models must be materialised before this command is useful.

## Usage

```bash
/wire:droughty-dbt-tests <release-folder>
```

## Prerequisites

- `/wire:droughty-setup` complete for this release
- dbt models deployed to the warehouse (`dbt run` complete)
- dbt project exists at `dbt_project_path` from setup

## Workflow

### Step 1: Confirm dbt Models Are Deployed

Before running, explicitly confirm deployment:

```
droughty dbt reads from the live warehouse — it needs dbt models to be deployed.

Have you run dbt and confirmed models are materialised in the warehouse? (yes/no)
```

If no:
```
Run dbt first, then return to this command.

If using dbt Cloud:  run the job from the dbt Cloud UI or API
If using dbt Core:   dbt run --profiles-dir . --project-dir [dbt_project_path]
```

### Step 2: Read Setup State

1. Read `.wire/releases/[release]/status.md`
2. Confirm `droughty.setup.status == complete`
3. Extract `dbt_project_path` from setup block

### Step 3: Run droughty dbt

```bash
droughty dbt \
  --profile-dir ~/.droughty \
  --project-dir .
```

Capture stdout and stderr. Surface errors verbatim.

### Step 4: Merge with Existing schema.yml

`droughty dbt` writes test declarations to the dbt project path. Check for existing Wire-generated `schema.yml` files:

```bash
find [dbt_project_path] -name "schema.yml" -type f
```

**If existing schema.yml files exist**, compare Droughty's output against them:
- **No overlap**: proceed, append Droughty tests
- **Partial overlap**: show a diff and ask:
  ```
  Droughty has generated tests for [n] columns already in schema.yml.

  Options:
    a) Skip overlapping columns — keep Wire tests, add only Droughty tests for uncovered columns
    b) Overwrite overlapping columns — use Droughty's pattern-based tests everywhere
    c) Show the full diff first
  ```
  Default recommendation: **option a** — Wire tests are semantically informed; Droughty tests add coverage for the rest.

- **Full overlap**: inform the consultant that Droughty adds no new coverage and stop.

**Test settings with droughty.** A project that uses droughty keeps `required_tests` on (`{"unique": 1, "not_null": 1}` under the warehouse `+meta` in `dbt_project.yml`) and sets `required_docs: false`, because droughty writes no model descriptions and rewrites `models/droughty_schema.yml` on every run. See `/wire:droughty-setup` Step 6.5. Where the project's `packages.yml` has `dbt_meta_testing`, check the result with `dbt run-operation required_tests` after `dbt build`.

Keep the test key the target schema file already uses (`tests:` or `data_tests:`). Never put both keys on one resource.

droughty does not generate tests in `_sources.yml`. Source files are written by hand, and `freshness` is their only test.

### Step 5: Verify Output

Report:
- Total tests generated
- Breakdown by test type (`unique`, `not_null`, `accepted_values`, date-range)
- Tables with zero tests (likely tables with no naming-convention columns)

### Step 6: Update status.md

```yaml
droughty:
  dbt_tests:
    status: complete
    tests_generated: [n]
    tables_covered: [n]
    merge_strategy: "[skip_overlap|overwrite|no_conflict]"
    completed_date: [today]
```

### Step 7: Confirm Output

```
## Schema Tests Generated ✅

[n] tests across [n] tables
  unique:           [n]
  not_null:         [n]
  accepted_values:  [n]
  date_range:       [n]

Merge strategy: [description of what was done with overlaps]

Next steps:
  1. Run dbt test to validate the generated tests pass:
     dbt test --profiles-dir . --project-dir [dbt_project_path]
  2. Review any accepted_values tests — Droughty infers valid values from current data;
     if the column can take new values in production, add them manually.
  3. Run Wire validation:
     /wire:dbt-validate [release]
```

## Output

This command creates or updates:
- `schema.yml` files in `[dbt_project_path]/models/` — test declarations appended
- Updated `droughty.dbt_tests` block in `status.md`
