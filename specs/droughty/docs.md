# Droughty Docs Command

## Purpose

Run `droughty docs` to use the OpenAI API to infer human-readable descriptions for all undocumented warehouse columns. Droughty uses column names, types, and surrounding context to produce descriptions, then writes them to a markdown file for consultant review before use. The output can seed LookML `description:` fields and dbt `schema.yml` descriptions.

## Usage

```bash
/wire:droughty-docs <release-folder>
```

## Prerequisites

- `/wire:droughty-setup` complete, with an OpenAI API key in `profile.yaml`
- Warehouse accessible

## Workflow

### Step 1: Read Setup State

1. Read `.wire/releases/[release]/status.md`
2. Confirm `droughty.setup.status == complete`
3. Check that an OpenAI API key was provided during setup

If no OpenAI key is configured:
```
Error: droughty docs requires an OpenAI API key.

Re-run /wire:droughty-setup [release] and provide your OpenAI API key when prompted.
```

### Step 2: Scope Check

Ask in chat if running on a large schema (> 200 tables):
```
⚠️  [n] tables are in scope. droughty docs will call the OpenAI API for each column.
This may take several minutes and will incur OpenAI token costs.

Proceed? (yes / no — or type the schema names you want to limit to)
```

If the consultant provides a subset of schemas, update `droughty_project.yaml` to limit scope for this run.

### Step 3: Run droughty docs

```bash
droughty docs \
  --profile-dir ~/.droughty \
  --project-dir .
```

This writes field descriptions to `field_description_path` in `droughty_project.yaml`, which is `.wire/releases/[release]/artifacts/droughty/field_descriptions/`.

Capture progress output. If the command exits non-zero, surface the error verbatim.

### Step 4: Verify and Summarise Output

Check that files were written. Read the generated descriptions and report:
- Total columns documented
- Any columns where Droughty could not infer a description (low-confidence or empty)

### Step 5: Update status.md

```yaml
droughty:
  docs:
    status: complete
    columns_documented: [n]
    low_confidence_count: [n]
    artifact: .wire/releases/[release]/artifacts/droughty/field_descriptions/
    completed_date: [today]
```

### Step 6: Confirm Output

```
## Field Descriptions Generated ✅

[n] columns documented across [n] tables
[n] low-confidence descriptions flagged for review

Artifacts: .wire/releases/[release]/artifacts/droughty/field_descriptions/

Review notes:
- Read through generated descriptions before using them in LookML or dbt — AI-inferred descriptions
  can be plausible but wrong, especially for abbreviated column names or domain-specific terms.
- Low-confidence columns are flagged inline. Prioritise those for manual review.
- These descriptions can be used as starting-point label: / description: values in LookML views
  generated by /wire:droughty-lookml.
```

### dbt documentation with droughty

In a dbt project that uses droughty, column descriptions are held once as doc blocks in `models/field_descriptions.md`. droughty writes them into the column descriptions of `models/droughty_schema.yml`. After review, add the descriptions from this command to `models/field_descriptions.md` as doc blocks (`{% docs <column_name> %} ... {% enddocs %}`). Do not edit `droughty_schema.yml` by hand: droughty rewrites it on every run.

droughty writes no model descriptions, so the project sets `required_docs: false` in `dbt_project.yml` and keeps `required_tests` on (see `/wire:droughty-setup` Step 6.5). Source column descriptions are not doc blocks: they are written inline in the hand-written `_sources.yml` files.

## Output

This command creates:
- `.wire/releases/[release]/artifacts/droughty/field_descriptions/` — one or more description files
- Updated `droughty.docs` block in `status.md`
