# data quality Validation Command

## Purpose

Validate that the data quality test plan generated by `/wire:data_quality-generate` is real and complete: every listed test actually exists in the dbt project, baseline coverage per `wire/skills/dbt-development/testing-reference.md` has no unresolved gaps, unit test coverage per the unit test rule in `wire/skills/dbt-development/testing-reference.md` has no unresolved Required gaps in any layer, and any `dbt_expectations` test is backed by the package actually being declared in `packages.yml`.

## Usage

```bash
/wire:data_quality-validate YYYYMMDD_project_name
```

## Prerequisites

- data quality must be generated (`/wire:data_quality-generate` complete)

## Sliced runs (`--slice`)

In a release built from tickets (`delivery: tickets` in `status.md`), this
command takes `--slice <slice>` and checks the tests for the slice's tables only
(`specs/utils/ticket_delivery.md`, "The `--slice` option"). Without
`--slice`, the workflow below runs as written.

1. The slice must be in `tickets.yaml`. If it is not, stop and list the valid
   slices.
2. Run every check below against the slice's part. A check that needs the
   whole release (a cross-model consistency check) runs against the slice and
   the parts it depends on, and says so in the report.
3. On a ticket branch, write the result (`pass` or `fail`) to the ticket
   record's front matter (`results:`) and the log row to the ticket run log
   (`iterations/<ticket>.execution_log.md`), not to `status.md` and
   `execution_log.md`.

## Workflow

### Step 1: Verify data quality Exists

**Process**:
1. Check that `data_quality.generate == complete` in status.md
2. Verify `test/data_quality.md` exists

**If not generated**:
```
Error: data quality not generated yet.

Run `/wire:data_quality-generate <project>` first.
```

### Step 2: Run Validation Checks

**Validation Checklist**:

| Check | Rule | Severity |
|-------|------|----------|
| Baseline coverage gaps table is empty, or gaps are tracked | Every row in "Baseline Coverage Gaps" has been either resolved (test now present in the dbt project's `schema.yml`) or has an explicit tracking note (e.g. a linked ticket) | Critical |
| Every listed test exists in the dbt project | Every row in "Baseline Test Coverage" and "Supplemental dbt-expectations Tests" corresponds to an actual test entry in the model's `schema.yml` (or a custom test in `tests/`) — no test is documented but never applied | Critical |
| Unit test coverage gaps table is empty, or gaps are tracked | Every row in "Unit Test Coverage Gaps" with gap **Required** (an integration or warehouse model with business logic, per the unit test rule in `wire/skills/dbt-development/testing-reference.md`) has been resolved with a real `unit_tests:` block, or has an explicit tracking note. **Advisory** rows (staging) never fail this check. **Check by hand** and **Classify by hand** rows need a recorded decision in Notes | Critical |
| `dbt_expectations` package declared if used | If any row in "Supplemental dbt-expectations Tests" uses a `dbt_expectations.*` test, `dbt/packages.yml` declares the `calogica/dbt_expectations` package | Critical |
| Primary keys have `unique` + `not_null` | Every model in the dbt project has its primary key covered — cross-check against `wire/skills/dbt-development/testing-reference.md`'s per-layer minimums, independent of what the test plan claims | Major |
| Severity assignments follow convention | Primary/foreign key tests are `error`; KPI-derived dbt_expectations tests tied to a named requirement are `error`; exploratory/nice-to-have tests are `warn` | Major |
| No orphaned test entries | No row in the test plan references a model or column that no longer exists in the dbt project | Major |
| Supplemental tests are grounded | Every supplemental dbt_expectations test cites a concrete justification (a named KPI, a stated time-series grain, a documented format) rather than being applied indiscriminately | Info |

### Step 3: Generate Validation Report

**Output Format**:

```
## data quality Validation: [PROJECT_NAME]

**Status:** PASS | FAIL

### Validation Results

| Check | Status | Notes |
|-------|--------|-------|
| Baseline coverage gaps resolved | ✅ | |
| Every listed test exists in dbt project | ⚠️ | [model]_pk unique test documented but not found in schema.yml |
| Unit test coverage gaps resolved | ✅ | |
| dbt_expectations package declared | ✅ | |
| Severity assignments follow convention | ✅ | |

### Next Steps

1. **Review with stakeholders**: `/wire:data_quality-review <project>`
```

### Step 4: Update Status

**Process**:
1. Read `status.md`
2. Update artifacts.data_quality section:
   ```yaml
   data_quality:
     generate: complete
     validate: pass | fail
     review: not_started
     validated_date: 2026-02-13
   ```
3. Write updated status.md

### Step 5: Sync to Jira (Optional)

Follow the Jira sync workflow in `specs/utils/jira_sync.md`:
- Artifact: `data_quality`
- Action: `validate`
- Status: the validate state just written to status.md (pass/fail)

## Edge Cases

### Validation Failures

If checks fail:
- Set validate status to `fail`
- List all issues, distinguishing "documented but not applied" (a gap in follow-through) from "applied but undocumented" (the test plan is stale relative to the dbt project)
- Suggest fixes
- User must fix and re-validate

### Test Plan Predates dbt Generation

If the test plan was generated before `dbt.generate == complete` (see `generate.md`'s "dbt Not Yet Generated" edge case), baseline and unit-test coverage checks cannot be run against real `schema.yml` files yet:
```
Warning: This test plan was generated from requirements only, before dbt models existed.

Re-run /wire:data_quality-generate <project> now that dbt models are available, then re-validate.
```

## Output

This command:
- Validates that the data quality test plan's claims match the real dbt project
- Confirms baseline schema-test, unit-test, and supplemental dbt_expectations coverage per convention
- Updates `status.md` with validation results
- Provides actionable feedback if issues found
